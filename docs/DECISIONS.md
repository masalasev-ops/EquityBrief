# DECISIONS.md

A decision belongs here when a later session could reasonably choose differently **and** the wrong choice would be invisible. Mechanisms with one obvious implementation, and anything a test already enforces, do not.

A decision is identified by its **bold name**, cited exactly. In code: `// see: Code owns every number`. In a document: `(see: Code owns every number)`. Same string either way, so `decision-resolves` covers both. Names carry no terminal punctuation, because a name ending in a period invites the paraphrase the check exists to reject.

A decision is changed only by another decision. Work that changes one writes a new decision, names what it supersedes, and moves the old entry to **Previously decided** in the same commit with its reasoning intact. Nothing here is struck through.

## Scope

**The universe is the S&P 500, and membership is fetched, not maintained** A published index is a fixed list rather than a filtered one, which keeps this a reporting tool rather than a screen. Membership is stored with join and leave dates so a name added last month is not shown as present in an older window.

**An announced index change takes effect on its effective date, and a joining name is stored from the announcement** The membership feed carries a rebalance before it takes effect, with the dates it takes effect on, and until the phase 5 sign-off every nightly stage and the read surface took a name for a member whenever its row had no leave date. The rebalance effective 21 September 2026 was on the feed by the 10th, so three names still in the index were stored nothing for and listed nowhere, and four names not yet in it were listed. A name is a member on a session when its join date is on or before the session, or is unknown, and its leave date is after the session or absent, which is the reading the membership loader already gave a past date. The stages that list, count or show the index read that. The stages that store what later stages read, the bars and their adjustment, read the wider set of every name that has not left by the session, which includes a name announced to join. That half is the choice a later session could reverse without seeing why: a backfill runs once, for a name holding no bars, so a name backfilled on its announcement and then not stored until its effective date would carry every session between the two as a hole nothing fills, and storing it early costs no nightly request, since the bulk file already carries it.

**One universe now, the seam for more built now** Every stored row belongs to a name, not to a universe, and every screen takes the selected universe as a filter. That is a table and a where clause today, and retrofitting it later would mean reconstructing membership for every stored night.

**Long-only share plans** The operator does not short and does not trade options, so the ladder builder has no branch for either.

**Section 4 of the architecture defines the report, and nothing outside the corpus does** The eleven sections, what produces each, and whether each costs money are stated there. Sections are added, removed or reordered by amending that table, and `architecture-conformance` checks the code against it. A hand-written example illustrates the rules and is never the thing to be reproduced: where an example and a rule disagree, the rule is right.

## Cost and when work happens

**The nightly run is arithmetic only** No model calls and no per-name network requests. Bars arrive in one bulk file and news in one feed request, so a night costs the same whether the universe is fifty names or five hundred.

**The night's zero-model-call rule bounds the arithmetic, and the overnight queue is carved out of it by name** Section 14's list runs to seventeen steps and step 17 calls the local model for every listed name whose research is missing or stale, while section 17's row read zero model calls in the nightly run, section 5's band said no model, and section 14's own closing note said no model is called. Four statements, and one of them is the step. The rule is kept and the step is carved, which is what 1.2 did for the backfill against the per-name limit rather than loosening a rule to fit its own exception. What the rule bounds is the arithmetic, being steps 1 to 16: those make no model call at all, and a night costing the same for fifty names as for five hundred follows from that rather than from anything the queue does. Step 17 runs after the arithmetic has closed and recorded its counts, makes local calls only, spends nothing, and no part of the arithmetic depends on it, so a queue that did not run leaves every figure above it unchanged and the run page says it did not. The carve is by name rather than by scope, so the scan that finds a model client keeps reading every other shipped file and the file the queue's client sits in is listed where a reader can see it (see: The outward-request scan names the files that may hold a client rather than dropping the patterns). A paid call from the queue is not carved and does not become so: the queue's own limit row says it makes none, and the local lane refuses a key, so the enforcement sits on the lane rather than on the step.

**Everything expensive happens when a name is opened** Reports are not generated for names nobody reads. A name never opened costs nothing beyond its share of the nightly arithmetic.

**Bars come from EODHD, bulk nightly and per ticker for the backfill** The provider is named in the architecture and the runbook and was never a decision, which left the route through it open to being reversed by a later session reading only the zero-per-name-call rule. The arithmetic is what settles it and belongs here rather than in a runbook table: bulk end-of-day for a whole exchange costs 100 weighted calls and a single-ticker historical request costs 1, so the nightly fetch takes the bulk endpoint at 100 against 500, and the one-year backfill takes the per-ticker endpoint at 500 against the 25,000 that replaying a year of past sessions through the bulk endpoint would cost. The two run opposite ways round for the same reason, which is that the bulk call is priced per request and the historical call is priced per name.

**Research is a stored document with an as-of date, not a cache** It costs money and produces a different answer each time it runs, so discarding it would change the report for no reason and leave nobody able to tell whether the analysis moved or the wording did. Every version is kept.

**Nothing expires on a timer** Research is rewritten when a filing appears, an earnings date passes, the name's news volume jumps above its own baseline, or the operator asks. A timer either refreshes work nobody needed or serves analysis written before a print.

**Deciding not to spend must not cost anything** The four staleness questions are answered from data the nightly run already computed, which is why the news pulse counter runs nightly and for free.

**Industry research is per theme, not per name** The passage about an industry's own pricing cycle is the same for every company in it, so one paid pass serves them all and refreshes when the first name needing it finds it stale.

**The spend cap is a stop, not an allowance** At the cap, research pauses and the page says so. A cap that can be exceeded is not a cap, and one that fails silently is worse than none.

## Numbers, claims and the models

**Code owns every number** Every figure in a report is computed from stored data or copied from a provider payload with its filing date. No model is ever asked for a number, a date or an estimate.

**Every number in written prose must exist in the facts file** Enforced by the claim checker. This is what lets a reader trust a paragraph a model wrote: any number in it traces to a computed value.

**A re-run replaces a night's facts file where the store now computes a different one** Until the phase 5 sign-off the assembler inserted with the conflict ignored, so the first file written for a night stood whatever a later run of that night computed, and its comment called that keeping the night idempotent. It was the opposite: a second run exists because the first went wrong, and on 2026-09-10 the attempt that stopped at the change detector had written every name's file from band sets a refetch had doubled, the run that completed after the band repair computed clean files, and every one of them was dropped on the conflict while the run log counted it written. NVDA's file for that night went on naming its immediate support twice. The facts file is what every number in a report is checked against, so it has to be what the store computes rather than what the first attempt computed. The assembler compares the hash of tonight's file with the stored one and, where they differ, deletes that row and inserts tonight's, so a re-run over an unchanged store writes nothing and keeps the change list beside each file, and a replaced file starts with no list until the detector writes it again. The alternative a later session might reach for, an update of the payload, would give the table a second updater, which the rule of one writer per operation forbids; the delete was nobody's. A re-run replaces only the newest night, because every stage computes over the store as it stands, so a night already followed by another cannot be recomputed by running it again.

**Every researched claim must name a stored source document** The claim checker drops any that does not, and the report's source list is generated from what was stored. Numbers are checkable against the facts file; claims are not, so the only available discipline is provenance, and the failure mode of automated research is a confident wrong sentence that nothing else would catch.

**Transcripts are opportunistic, never a dependency** The earnings press release filed with the results announcement carries the guidance, the segment tables and management's prepared framing, and it is free. A verbatim transcript adds the analysts' questions, which is where management is pressed hardest, but only some companies file one. Where it exists it is read from the same free fetch; where it does not, the section is written without it. No provider is bought for it.

**The local lane's scope is a setting, and the overnight queue writes whatever is in it** Section 13 assigns work per section rather than per pass, so which sections the local model owns is configuration. On a machine with 24GB of graphics memory that is the short-prompt work: naming what caused a move, pulling the segment figures out of a filing, writing the figure keys. Synthesis is not in it, because a model small enough to leave room for the whole evidence set on that card is the case already named as producing something fluent that says nothing. On a machine that can hold a large model with a long context, synthesis moves into the local lane by changing the setting and the overnight queue starts writing it too. The build does not change between those two machines, and the fixture comparison rather than the memory figure decides whether a section should move.

**A research record is written and dated per section, not as a whole** On the current machine some sections are drafted locally overnight and others are written by the paid model days later when a name is opened, so a single as-of date and a single model name for the record would be false. Each section carries its own state, its own date and the model that wrote it, which is what lets the report state exactly what you are reading and stops the staleness judge treating a half-written record as complete.

**The overnight queue writes a free first draft; the paid model is for names you get serious about** After the nightly arithmetic, the local model works through the names on tonight's list whose research is missing or stale, in order of how many reasons fired, and writes their narrative sections at no cost. In the morning those names open complete. Opening anything else, or pressing refresh on a name whose local draft is not good enough, runs a paid pass on demand. The record already stores which model wrote each section, so the report says which you are reading and offers the better one, and no new machinery is needed for either path.

**The overnight queue is bounded by time, not by a count of names** One pass may take four minutes and another twelve, so a name count does not bound anything. The queue works in priority order until a stated number of hours has passed and then stops; whatever is left is first in line the next night or is written on demand when you open it. A busy night degrades by leaving names for later rather than by running into the morning.

**The overnight run holds the machine awake and reports whether it ran** A laptop left alone will sleep, and a nightly job that silently did not happen is worse than no nightly job, because nothing announces it. The run asserts wakefulness while it works, and the run page states the previous night's outcome including how many queued passes completed and how many were left.

**Two models for two jobs, and the research model is DeepSeek V4** A local model on the operator's GPU writes prose from numbers, which is small and free. DeepSeek V4 does research, which is a large-context job a local model does badly. Chosen on cost: a research pass is a few cents rather than a few tens of cents, which puts a year of normal use in the tens of dollars. The tier, Pro or Flash, is left to the fixture comparison rather than decided here, because the difference between them is a few dollars a year and the only thing worth choosing on is the quality of the two-cases section.

**A research pass is split by section difficulty, not run wholesale on one model** The dividing test is whether the answer sits inside one document or has to be built across several that disagree. Classification and extraction stay on the local model at no cost, and each such call carries only the documents that section needs rather than the whole evidence set, which is what keeps it inside a consumer card's memory. Synthesis goes to the paid model, because a small model given contradictory evidence produces something fluent that says nothing. Figure 12.2 shows where the line falls. The line itself is provisional: the frozen fixture makes it measurable, so each section is run both ways against the fixture and the boundary is settled by that comparison rather than asserted here (owes: The research lane boundary measured against the fixture both ways).

**The local model answers at an OpenAI-compatible endpoint, and which model answers is configuration** The lane split was a setting with no shape, so nothing said how a section reaches a model at all. The local model is reached over HTTP at an OpenAI-compatible chat completions endpoint on the operator's own machine, which is the interface LM Studio, `llama.cpp`'s own server and Ollama all serve, so the runtime is the operator's choice and not the build's. Configuration carries the base address, the model identifier and the per-call timeout, and nothing else. The model is Qwen 3.5 9B on the machine this is first built for, and a larger or later one is a setting rather than a change to this entry (see: The local and paid boundary is a property of the machine, not of the design). The identifier is stored on every section the model wrote, which is what makes a comparison between two models a reading of the record rather than a memory of which was running. A local call needs no key, and a key configured for the local lane is refused rather than sent, because a local endpoint that authenticates is an endpoint on somebody else's machine and the queue's zero-cost property rests on this lane being free.

**The local lane is a configured list of section names, and the prose writer writes whatever the list holds** Which sections the local model owns is a setting, and a setting with no shape becomes whatever the first implementation does (see: The local lane's scope is a setting, and the overnight queue writes whatever is in it). It is a list of section names in configuration, read once per pass, and the writer takes the list rather than deciding section by section, so moving a section between lanes changes a value and touches no code. On the machine this is first built for the list holds the cause of each large move, what the company sells, the segment commentary and the key under each figure, which is the short-prompt work figure 12.2 puts on the left (see: A research pass is split by section difficulty, not run wholesale on one model). The short version is not in it, and that is the list's value rather than a fact about the component: section 4, figure 12.2's table and section 15.12 each put it in the paid lane, while the prose writer's catalogue row said it wrote that section on the local model at no cost. Neither side was a design fact, so neither is superseded and nothing is corrected except the row, which now names the lane where it named the section. A section in the list the machine cannot hold is refused before the pass starts and left for the paid path, which section 18 already promises, so a list edited past what the card holds degrades rather than failing.

**The research model is one interface with an implementation per wire format, chosen by configuration and never falling back** The endpoint was already configuration and that is not enough, because two research providers do not share a request shape, so the choice of provider is a code path even where the address is not (see: Two models for two jobs, and the research model is DeepSeek V4). The research model is one interface with one implementation per wire format, and configuration names which provider answers. It is resolved in the one place the on-demand feeds are resolved, refusing in both directions, and it never falls back from one provider to the other. A fallback would make the model that wrote a section unknowable from the fact that the section exists, and every section is already dated and stamped with the model that wrote it for exactly that reason (see: A research record is written and dated per section, not as a whole). A provider named in configuration with no key refuses at startup rather than at the first pass, which is the shape the credential path has carried since 2.1. The switch is also what makes the lane boundary measurable rather than asserted, because the recording is keyed on the canonicalised request, so one section over one stored evidence set through two providers is two records a reader can set side by side.

**A stored source is not automatically an admissible one** Requiring that a claim name a stored document proves where a sentence came from, and proves nothing about whether that document is worth believing. A search for a company by name returns machine-generated price forecasts, broker marketing pages quoting contract-for-difference prices rather than the stock, year-old articles carrying a previous fiscal year's guidance with no visible date, and summaries written by other AI systems. Each of those would satisfy a bare provenance rule. So admissibility is a second test, applied before a document is stored: deny algorithmic price predictions, broker and platform marketing pages, AI-written summaries, and quote or hub pages carrying no article; require a publish date and reject anything outside the window the pass asked for; prefer the company's own filings and releases, then established financial press, and make the pass state why it used anything else. A document that fails is not stored, so a claim resting on it cannot be written.

**Gated sources are out of scope, and access is ranked before reputation** Paywalled and login-walled sites cannot be read by an automated pass and no attempt is made to work around them. The order of preference follows access rather than prestige: filings and company releases first, which are free, complete and fetched by ticker rather than searched; then the licensed news feed, where the provider delivers article text under its own distribution agreement so the paywall question does not arise; then the open web, which is where gating actually bites. What is genuinely lost is the analyst-opinion layer and primary industry research. Where the substance of a gated report reaches free outlets as secondary coverage, that coverage is the source and is marked as second-hand rather than presented as the original.

**Two source lists govern the open web, and the licensed feed is a channel rather than a list** Filings and company releases need no list, since they are fetched by ticker. A company-news list governs reporting about a company and an industry list governs theme material, because the publishers who write about memory contract pricing are not the ones who write about quarterly earnings, and splitting them keeps a theme search from returning earnings coverage and the reverse. Every list carries a review date, because sites are acquired, paywalled and abandoned, and a list nobody revisits silently narrows what the system can see.

Two is what the previous entry described and three is what it was called, which is the whole of contradiction J. What is new is where the lists apply. The 1.7 measurement found that the licensed news feed delivers 1,173 of 1,253 articles under one domain, and that the domain is the aggregator that carried the article rather than the outlet that wrote it: the writing outlet appears inside the text where it appears at all. So a domain list over the news feed would hold three entries and would filter nothing, and filtering the feed by domain would discard the whole feed or none of it. The lists therefore govern the search tool, which is where a query can return a football club or a forum post, and the news feed is admitted as a delivery channel with the per-document admissibility test doing all of the work on its articles. (see: Admissibility is judged per document, after the fetch, and never per publisher)

**A list of publishers is a noise filter, never a correctness test** The list decides which sites a search may return; the per-document test decides whether a particular article may be believed. Both are needed and neither substitutes for the other, because a publisher that belongs on any reasonable list also runs promotional opinion pieces and syndicates other people's, and a trial search returned exactly that from a well-regarded name. A list also has to be of sites that are reputable and fetchable, which is a smaller set than reputable: the most authoritative names in this field are the gated ones, so a list assembled by prestige is substantially a list of pages that return nothing.

**Admissibility is judged per document, after the fetch, and never per publisher** A publisher that runs ordinary financial journalism also runs machine-generated price forecasts, so denying the domain throws away the good with the bad and allowing it admits the forecasts. A search tool's domain filter cannot express this, since it operates on the site rather than the article, which means search parameters reduce noise and the admissibility test does the actual work, on the document, after it has been retrieved.

**Theme material comes from a search tool, and per-name material never does** A per-name pass reads filings and news fetched by ticker, which is exhaustive over a date range and cannot return the wrong company. An industry's own pricing cycle is published by research firms and filed with nobody, so that one section needs open search. The tool is Tavily, called as one more fetching tool inside the research loop; its results are stored as documents exactly like a filing or an article, so the claim checker and the admissibility test apply unchanged. Volume is a few hundred searches a year against a free allowance of a thousand a month, so cost is not a factor and will not become one. A self-hosted meta-search is the fallback if that allowance changes, since nothing in the design depends on which tool answers.

**A theme search is scoped by parameter, not by hope** Trial searches showed what an unscoped query returns: for a two-letter ticker, results about a football club; for a company name, a machine-generated price forecast, a broker marketing page, a year-old article carrying a previous fiscal year's guidance, and another AI system's summary. So a theme search names the industry rather than a ticker, is bounded by an explicit date range, restricts results to the industry source list, and requests full page text rather than snippets, because a snippet cannot be stored as the document a claim rests on.

**The model never fetches; components fetch and hand it documents** The research model has no web search of its own, and this is the right shape regardless: every document entering a pass is stored as it is fetched, which is exactly what the claim checker needs to verify a claim's source. A model that searched for itself would produce claims backed by documents nothing kept.

**Queued work runs off-peak, and every schedule is written in UTC** Research rates double during two fixed windows that fall late at night in Eastern time, so interactive reading after the close is never billed at peak. Non-interactive passes are scheduled into off-peak on purpose, in UTC, because a schedule written in local time moves into peak when daylight saving changes.

## Data

**One year of bars, and no more** Every level in the report comes from a sixty-session window, so a longer history was never needed to produce one. A year covers the 200-day average and gives the level window headroom, and costs about ten megabytes for the whole index.

**Bars are never interpolated** A gap stops computation for that name and is reported as a gap.

**A gap is a session the exchange traded and the store does not hold** Detection is against the exchange's trading calendar rather than against the rows themselves, because a run of stored dates is self-consistent whatever is missing from it and a store holding four days of a five-day week looks exactly like a store holding four days of a four-day week. Two behaviours follow and they are different things: the fetcher refuses to store a series arriving with an interior session missing, and every computation over a name whose stored series has a gap stops and reports the gap's date. The state is derived on read from the stored sessions against the calendar rather than kept in a column, so nothing has to be brought back into step with the bars after a refetch fills the hole.

**A session the night finds missing is fetched in bulk before tonight's** A night that does not run leaves every name short the same session, and the calendar the store can observe is the union of the dates its names hold, so a session every name missed is one it reads as a closure: the hole is invisible exactly when it is widest. So the fetcher compares the newest session the store holds with tonight's against a table of the exchange's closures pinned in code, fetches each session between them in bulk before tonight's, and stores all of them in one transaction. The provider serves an older session's bulk file as prices, which the phase 5 sign-off measured rather than assumed. The cost is one request per missed session, which grows with the nights missed and never with the names, so it is not a per-name call. A missed session whose file cannot be fetched, or carries none of the index, stops the night by name, because a gap stops computation rather than being counted across. The table covers a stated range and refuses a weekday outside it rather than guessing, since a closure read as a session is a day asked for and never answered, and a session read as a closure is a hole nobody fills.

**The stored series is adjusted** One price set per bar and it is the provider's adjusted one, which is why `bar` carries four price columns and no adjusted variant. An unadjusted series never diverges from itself, so storing one would make the corporate action checker pointless and leave the levels drifting away from every chart the operator compares them against. The cost is that stored history is restated by the provider whenever an action lands, which is the thing the nightly check exists to catch (see: Adjusted history is re-fetched after a corporate action).

**Adjusted history is re-fetched after a corporate action** Splits and dividends change adjusted closes, so stored history silently diverges from the provider unless a nightly check catches it.

**Fundamentals are stored with the filing date they came from** Providers restate. Keeping the filing date is what makes it possible to know later what you knew at the time.

**A calendar event is fetched once for the whole index, and the calendar holds provider events only** Four components declare a `calendar` read, `SCHEMA.md` declared no such table and nothing wrote one, which is contradiction E. The table is written by one component on the nightly path, fetching the whole index's dated events in one request over the horizon rather than one request per name, because the earnings date is needed nightly by the ladder builder and the shortlist builder and a per-name call there would break the rule the whole design rests on. It holds what the provider files and nothing else. A `kind` column carries provider event kinds only and a researched event never acquires one: the report's Dates section draws on the provider calendar and on dated items from the research record, and those two meet at the report surface, which is where section 4 already has them meeting. A researched date written into this table would be a claim with a source that the one instrument built to verify sources cannot see, and it would give a nightly store a second writer against the rule that a store has one writer per operation. The `kind` restriction is stated rather than implied because the first person wanting a product launch in the Dates section would otherwise add a kind for it, and the second origin would arrive without a decision.

**Every computed table's writer is its own deleter** Section 16 states one year, recomputed nightly and kept for the harness, over indicators, swings, volume profile, levels, ladders and moves, and `SCHEMA.md` gave Delete to nobody for any of them, which is contradiction A and contradiction H a third time in a third table. The four that exist split on grain and the split is what makes this due now: `indicator` keys on ticker, session and name and `swing` on ticker, session and direction, so both replace with the series and grow only as it does, while `volume_profile` keys on ticker, as-of date and band and `level` on ticker, as-of date and low edge, so both write a new set every night and replace nothing. At the bands a name this fixture averages, five hundred names put something of the order of three and a half million rows a year into a store nothing was declared able to reduce. `ladder` is the fifth and keys on as-of date, so it grows the same way, which is why the ruling lands with the checkpoint that adds it rather than at 5.2 where the last of the six arrives. Each builder drops the rows that fall out of the window on the night they fall out, which is what `BarFetcher` and `NewsPulseCounter` already do for the two tables that carry a stated retention and an owner to enforce it. A retention window nobody owns is a table that grows forever while the file says it does not.

**Your own listing history is kept forever** Which names reached which levels on which nights, and what happened next, is a record no provider sells and the only evidence that will ever settle whether a reason is worth keeping.

**News is one dated query, paged to cover the day, and attributed to names locally** The feed is queryable by date with no ticker, which was probed on the operator's key at 1.5 rather than assumed: one request over a date range returns articles for the whole market, every row carries a `symbols` array naming the tickers it is about, and the response shape is identical whether or not a ticker was asked for. So a night makes one dated query and fans the rows out to names in code, and the per-name cost of news is zero calls rather than one call per name. The alternative, a request per ticker, would put five hundred calls on the nightly path for the same articles and would break the rule that a night costs the same for fifty names as for five hundred. The row also carries the article text, so the source document a claim rests on arrives with the row rather than needing a second fetch, which is what makes admissibility judgeable at all without spending again.

One request does not carry a day, and the pages are counted. 2.5 measured it: one dated request for a single session returned exactly 1,000 articles, which is the provider's cap, over 3,232 distinct symbols. A count taken from a capped request is a count over whatever the cap happened to include, which is a figure over a mixed population and is not stated at all. So the query is paged until the day is covered, every page is counted, and a day that reaches a stated maximum page count refuses and says so rather than reporting a truncated count as a whole one.

The page count is a function of the day's news volume and not of the universe, and that is what keeps the cost rule true. One request already attributed 3,232 distinct symbols against an index of 503, so the feed is market-wide and adding names to the universe adds no articles to it. A feed that pages counts every page, and a page count that grows with the index is a per-name call; this one does not grow with the index, and `nightly-cost` measures it over two universe sizes to show that rather than to assert it. What the measurement does falsify is the arithmetic written before it: section 14's step counting today's articles said one request, and section 17's weighted-call row priced news at one request weighing 5. Both now read per page, with the driver named, and ten pages at weight 5 is 50 against an allowance of 100,000.

## Feeds and the wire

**A feed is unavailable when it does not answer, and wrong when it answers with something else** Section 18 promised a behaviour for a feed that is unavailable and never said what unavailable is, which left four different events sharing one row and no test able to induce it. Unavailable is a refused connection, a request that passes its timeout, a rejected request rate, and a status the provider uses for its own faults. Every one of those is a night that did not happen, and the answer is the one section 18 already gives: keep last night's bars, mark every name stale, still serve the app, and say so on the banner with the data date. Wrong is an answer that arrives and parses and is not the answer asked for. That is a night that would look like it happened, and the answer is the opposite: refuse the payload, leave the stored series exactly as it was, and name what was wrong on the run log. The two are kept apart because folding them would give a payload carrying yesterday's session the "keeps last night's bars" behaviour, which is right, and lose the part that matters, which is that something arrived and was rejected. One is a fact about the network and the other is a fact about the provider, and only the second is worth a person's attention in the morning.

**A feed is tried three times with a doubling backoff, and the night has a deadline it cannot move** Every feed interface accepts a cancellation token and nothing supplied one, so a night that hung on a socket hung until somebody looked. At most three attempts per request, the first two failures waited out for two seconds and then four, and each attempt bounded by a thirty-second timeout. Thirty seconds because the bulk file for a whole exchange is the largest thing the night fetches and is a few megabytes: far outside a healthy fetch and far inside the night. Three attempts because the failure a retry is for is a transient one, and a fourth attempt is a slower way of learning what the third said. What is retried is a refused connection, a timeout, a rejected rate and the provider's own fault statuses; what is not retried is a rejected key or a route the provider does not have, because a wrong key is wrong three times and the retry only delays the message that says so. The night as a whole carries a deadline of fifteen minutes, which is three times the wall clock the limits table states for five hundred names, so the deadline stops a night that has hung rather than one that is merely slow. At the deadline the night stops, names the step it was on, and exits non-zero.

**The night runs at a fixed UTC instant, moved only when a night finds the day's file not yet posted** Section 14 scheduled the night with Task Scheduler after the US close, which named one platform's mechanism and a local time, against two hard rules at once. The schedule is a UTC instant, registered with whatever scheduler the machine has, and the application neither knows nor asks which. The instant is the one `RUNBOOK.md` states, after the close at both ends of the year with a margin for the provider to post the day's bulk file, and it stands while nights succeed. It is not settled by measuring the posting hour, because a night that finds the file already posted says only that it was there by then: five such nights bound the hour and settle nothing, and the obligation that waited for them had a trigger whose firing could not answer its own question. What moves the instant later is a night refused because the day's file carried none of the index at the scheduled instant, which is the provider not having posted yet. That refusal is on the run page's stale-and-failed region the next morning, and the session is not lost, because the next night fetches it as a missed session. The instant is a setting in the runbook with its reason beside it and not a figure in this entry, because a number written into a decision is the shape that gets cited later as though it were settled.

Supersedes **The night runs at a fixed UTC instant set after the provider posts the day's bulk file**, moved below with its reasoning. The line was missing when this entry was written, which the phase 5 sign-off reviewer found: the old entry was moved and nothing here said which it was.

**A night on a day the exchange did not trade fetches nothing and exits clean** The exchange trades on weekdays less its closures, so a night scheduled every day falls on a day with no session every weekend and every holiday. Until the phase 5 sign-off such a night asked the provider for the day's file, was refused at the fetch because the file was dated the session before or held none of the index, and exited 1: the scheduler recorded a failure every weekend, and a missed Friday caught up by a Saturday night was rolled back with the Saturday's refusal. The night now asks the closure table whether its session was traded before it fetches anything, and on a day that was not, it writes one run log row naming the day, fetches nothing, and exits 0. The row carries an outcome of its own rather than `ok`, which under the closing stage would say the night's counts were recorded, and rather than a failure, because nothing is owed on such a day. Registering the task on weekdays only saves the weekend's rows and is the runbook's business; the night does not rely on it, because a holiday falls on a weekday. A weekday the table cannot place is still refused, since the table exists to refuse rather than guess.

**A feed that pages counts every page, and a page count that grows with the index is a per-name call** Every feed interface counts its own requests and none said what happens when a payload arrives paged. The count includes every page, so a feed that starts paging reports the truth and the limits row stops reading as one. The limit itself is restated to say what it always meant: the count does not grow with the number of names. A payload that pages because it is large is bounded by the payload; a feed whose page count rises as the index does is a per-name call wearing a different name, and it is a defect under the same rule rather than a new exception to it.

**The night's cost is counted in weighted calls against the stated daily allowance** `RUNBOOK.md` states the provider's allowance as 100,000 weighted calls a day and gives the weight of each endpoint, and no code read either figure, so nothing stopped a night spending a month's allowance and nothing would have said it had. Each feed declares the weight of the endpoint it calls, the run log records the night's weighted total beside its request count, and a stage that would take the running total past the allowance does not start. It is denominated in calls rather than in money because this provider sells a flat subscription with a call allowance, which is a different shape from the research provider whose cap is money and whose rate doubles at peak. The local stop exists because the provider's own stop is a rejected rate, which arrives as an unavailable feed and loses the reason.

**The outward-request scan names the files that may hold a client rather than dropping the patterns** `nightly-cost` scans every shipped file for `System.Net.Http`, `HttpClient`, `WebClient`, `HttpRequestMessage` and the socket constructor and reports zero, which is true only while no feed reaches the network. The first live feed turns a green check red, and there were two shapes available. Deleting the patterns leaves a check that reports the absence of a scan as the absence of a client, which is the under-reporting failure `coverage-reported` exists to catch, arriving inside the check that carries the nightly path's own claim. So the exemption is named instead: one file per live feed, listed in the check, with every other shipped file still scanned and the scanned count floored where it is rather than lowered. The list is asserted to hold exactly the feed implementations, so a file added to it that is not a feed fails rather than passes quietly.

**The on-demand feeds are resolved in one place, as the nightly feeds are** The night's six feeds are one record resolved once from configuration, live against a capture, refusing a fixture folder that does not exist rather than resolving to the live path and refusing to fall back to a capture on a live run. The research work reaches five more surfaces, being the fundamentals endpoint, the filings archive, the search tool and the two model lanes, and not one of them is nightly, so none belongs on that record. They get a record of their own, resolved the same way and for the same reason: what a pass ran against is a fact the run log has to carry, and a client constructed inline is a choice nobody can read afterwards, which is where the night's own source selection lived until 2.6 and is why there was no selection. The overnight queue is the one research surface a night reaches, and it takes the local lane through this record rather than holding a client of its own, so a night's model calls are attributable to the same resolution every other call it makes is.

## Levels and the plan

**Levels come from four sources: swings, moving averages, retracements of the last two swings, and heavy volume shelves** The first three are prices the chart has visited or arithmetic on them. The fourth is where the shares actually changed hands, which is the only one of the four that says how many people have a reason to act at a price. A support band holding a large share of the period's volume is defended by holders at their cost; a range above the price where almost nothing traded is one price moves through quickly. A level builder without a volume profile can state neither.

**A heavy volume shelf creates a band of its own and also strengthens one it coincides with** Section 9.1's first step collects every price band holding an unusually large share of the period's volume as a candidate, and a candidate is what a band is merged from, so a shelf with no swing, average or retracement anywhere near it is a band in its own right. Its last step adds a point where a band holds a shelf, which is the ranking half and is a different question from whether it creates. Both readings were available and they produce different band sets, so the level builder is a different component depending which is taken. Creating is the one the four-sources decision already names: a source of levels that could only rank would be three sources and a modifier. It is also the reading the volume argument requires, because the range where almost nothing traded is a statement the report can only make about a band that exists on volume alone. The cost is that a name whose volume is evenly spread produces no shelf band and loses nothing, while a name with one dominant shelf gains a band no other source would have found, which is the case the whole profile was built for.

**The volume profile accumulates over the same sixty sessions as the level window** One window and not two. The shelf is a candidate the level builder merges alongside swings and retracements, and those come from the last sixty sessions, so a shelf drawn from a different span would place a band on volume from sessions no other member of the level table can see. The profile's own share figures would then be shares of a period that is not the period the rest of the chart is drawn from, and two numbers on one page would silently mean different things. The moving averages remain the stated exception, reading the full stored year, and they are exempt because an average is a price rather than a share of a period and the limits row already says so. Written as a decision rather than left to the builder because `SCHEMA.md` gives the profile an as-of date and price bands and never says over how many sessions volume is accumulated, so nothing would have caught the two windows drifting apart.

**The volume profile is twenty bands across the window's own range** A fixed count of bands spanning the window's high to its low, rather than a fixed price width. The count has to be the same for every name because the shelf threshold is one number for all five hundred: "at least twice its even share of the period's volume" means a fifth with five bands and a fortieth with forty, so a threshold stated once and read against band counts that differ per name is a threshold that means something different for each of them. A fixed width in money has the same defect from the other end, putting three bands on a forty dollar name and three hundred on a four thousand dollar one. Twenty is the number section 15.5 already describes when it says a support band can hold a fifth of the period's volume in a twentieth of its price range, so the figure is read out of the document rather than invented beside it, and it is also what a histogram of twenty rows can be read by eye where two hundred cannot. The band edges are rounded to the four places the stored prices carry and every band takes two adjacent members of one array of twenty-one edges, so the bands tile by construction rather than by two roundings agreeing. Written as a decision because `SCHEMA.md` gives the profile a band low and a band high and never says how many bands there are, and section 9.1 settled the window without settling this, so the shelf threshold rested on a number no document held.

**A name with fewer than sixty sessions gets no volume profile** Not a profile over what it has. `share_of_period` is a fraction of the window's total volume and the column carries no denominator, so a row computed over twenty sessions sits in the same table as one computed over sixty and reads identically. That is a figure over a mixed population, which `CLAUDE.md` already forbids stating at all, and it would reach the level builder as a shelf whose share is a share of a different period. The absence is visible instead: the name has no rows and the run log's detail carries the count of names skipped, so a night where a backfill failed shows as a jump in that count rather than as a set of quietly shorter periods.

**A retracement is drawn between the last swing high and the last swing low** The window's most recent high and its most recent low, in whichever order they occurred, with the five fixed fractions taken across the distance between them. The phrase in the architecture, "the retracements of the last two swings", reads equally as the last two swings of any kind, and that reading produces a retracement between two highs or between two lows, which is a fraction of the distance between two prices that no one retraced. A retracement is a partial reversal of a move, so it needs the two ends of a move, which is one high and one low. Where the window holds no swing of one of the two kinds, the name has no retracements that night rather than retracements drawn from a substitute, because a substitute end is an invented move.

**A volume shelf enters the merge as one price, the midpoint of its band** Section 9.1's first step collects "every price band holding an unusually large share of the period's volume" as a candidate, and its key says a candidate is a single price with a reason to matter. Those two sentences describe different things and `SCHEMA.md` settles which: a member carries one kind, one price and one date, so a shelf reaches the merge as one price like every other candidate. The midpoint rather than an edge, because neither edge is where the volume is and choosing one would put the band systematically low or systematically high. The alternative, contributing both edges, is not academic: it makes the resulting band exactly the shelf's own width whenever nothing else is near, and a shelf's width is the window's range divided by twenty, which is an artefact of how the profile is cut rather than anything the price did. Measured on the fixture, two of the three names have a shelf narrower than half a typical day's move, where the two readings agree, and the third has one twice that, where they do not. The shelf's identity is not lost by this: the member record says it is a shelf, the strength step reads the coincidence, and the profile itself still carries the band's edges and its share.

**A member's date is the session its evidence occurred on, and a figure recomputed nightly has none of its own** A swing carries its own session, a touch carries the session that reached the band, and a retracement carries the later of the two swings it is drawn between, that being when the move it retraces ended. A moving average and a volume shelf are figures over the window rather than events, so they carry the as-of date because `SCHEMA.md` requires every member to have one. The consequence is the whole reason this is written down: section 9.1's strength score adds a point for "a member from the last twenty sessions", and an average dated as-of is always from the last twenty sessions, so awarding the point on date alone would hand it to every band holding an average, which is every band near the price on any night. A point every band scores ranks nothing. The point is therefore awarded on the three kinds whose evidence occurred, and the two computed nightly cannot win it.

**Touches strengthen a band and never create one** A session that reached a band is evidence for it, which is how the report cites dated lows that are not swings in their own right.

**A tranche is a support band, and its stop is a daily close below the low edge of the next band beneath it** Close rather than touch, because a name moving six percent on a normal day dips through levels intraday every week, so a stop on a touch is taken out by noise and a stop on a close is taken out by a decision. The next band down rather than just below the tranche, because anything closer than a typical day's move is inside the noise.

**A moving average is a level on the chart and never an anchor for a tranche** A short average follows the price by construction, so a band anchored only on one sits near the price regardless of what the price has done. Measured on the worked example's own bars, the close was within half a typical day's move of its 20-day average on seventeen of thirty-one sessions, so a tranche placed there would make the first condition fire about half the time on nothing having happened. Averages stay on the chart because a reader wants to see them; they simply do not decide where to buy.

**A support band whose low edge is below the price carries a tranche, even when the band contains the price** A band the price is already trading in is exactly where the first step of a staged purchase belongs, so eligibility turns on the low edge rather than the whole band. In the worked example this is the band from 900 to 940 with the price at 933 inside it. The band keeps its full width, because a fill can land anywhere in it.

**The trailing stop is the higher of the band beneath and the last swing low** In a range the stop is the range floor, which is the low edge of the next support band beneath the tranche; in an uptrend it trails, and what it trails to is the higher of that band and the most recent swing low beneath the tranche; in a downtrend there are no tranches. Kaminski and Lo, Journal of Financial Markets, 2014, show a stop reduces expected return under a random walk and can add value where returns trend, so one stop rule for both cases is wrong in one of them. Taking the higher of the two rather than the swing low alone is what keeps the trailing half meaningful. Read literally, trailing the last higher low puts the stop wherever that low happens to be, which on a name that has run a long way is far below the band beneath and is looser protection than the range rule gives, and a trailing stop that can sit below the range floor is not trailing anything. The committed fixture holds the case: MSFT's third tranche has its last swing low a hundred points under the band, and the literal reading would put the stop there.

Supersedes **The stop rule depends on the trend state**, moved below with its reasoning. The code has run this rule since 4.5 and no spec said it: figure 10.1 read that the stop trails the last higher low, the superseded decision said the same, and the phrase "higher of" appeared only in two records, a source comment and an expectation note. A decision is changed only by another decision, so until this one the rule the code ran was a rule the corpus did not hold.

**An exit closer than two typical days' moves is listed but not traded** A move smaller than two ordinary days is inside the noise, so the level is worth naming on the chart and not worth paying a spread to act on.

**The plan places a position and never sizes one** The sizing paragraph is worked arithmetic from a risk budget the reader chooses.

**The second book is keyed to a dated event, and an earnings print is the only kind on file** It has its own setups, its own stops and a horizon of days, and it never merges with the position book, because holding a momentum entry through a print is the thing the separation exists to prevent. What is new is what the book is keyed to. Section 10 said the second book is keyed to dated events, of which an earnings print is one, and left where the other kinds come from to be settled here. They come from the calendar and from nowhere else, so the kinds the book can carry are the kinds the provider files, which today is the print. A dated item a research pass found is a claim with a source and lives in the research store, and it reaches the report's Dates section without ever reaching this book. Supersedes **The earnings trade is a second book**, whose name said earnings where its own body already said the separation is about carrying a momentum entry through a date.

**A ladder row is written for every index member every night** Carrying the trend state, and a plan that states why it is empty where it is empty. Section 18 says a name with no eligible band produces no ladder and the report says why, and a row that is absent says nothing: an empty plan stating its reason and an absent plan are different objects and only the first is readable on a screen. The same shape as the listings row written for every name whether or not a reason fired, and for the same reason. Tonight's label is compared against last night's by the trend-changed reason, so a name whose band went ineligible has no yesterday unless a row was written on the night it had none, and the transition into and out of a downtrend is exactly the one that changes the whole plan. The cost is one row per name per night, which is the order the listings table already accepted.

**The trend state is read from the averages and the last two swings, and a name that cannot be classified says so** Uptrend when the close is above the 50-day average, the 50 is above the 200, and the most recent swing low is above the one before it. Downtrend is the mirror, close below the 50, the 50 below the 200, and the most recent swing high below the one before it. Range when every input is present and neither holds. Not classified, with the reason recorded, when an input is absent: fewer than 200 bars, so there is no long average, or fewer than two swings of the kind the rule reads. The fourth value exists rather than a default because the corpus already refuses this trade elsewhere: an average of sixty bars labelled 200-day is a lie, and a name labelled range because nothing could be measured is the same lie one level up. A name that is not classified carries no tranches, so the label decides a plan and cannot be a guess. The swings are read as of the date through the same reader the level builder uses, so nothing sees a swing confirmed later.

**The trend classifier returns its label to the ladder builder** The catalogue said it returns the label to the facts assembler, which is built at 5.3, a phase after the screen that draws the label. It writes nothing, `LadderBuilder` stays the single writer `SCHEMA.md` already declares for `ladder`, and the facts assembler reads the label off that row when it arrives. A classifier that wrote would give one label two homes the moment a ladder row also carried it, which is the second statement of one fact this corpus has spent three phases removing.

**A tranche's condition is the pattern the price has made at its own band** Figure 10.1 names a fixed list of four and says nothing about which one a given tranche gets. Each is decided by the band's own recent history, tested in a stated order so that exactly one matches: available now, where the close is inside the band; a failed breakdown back into the zone, where a session inside the lookback closed below the low edge and the close is back at or above it; the first close back above the zone after a dip, where the close is above the high edge and a session inside the lookback traded into the band; and the second day after a shock once the first day's low has held, where a session inside the lookback moved more than the shock multiple and the band is the one it landed on. Exactly one, asserted in both directions rather than left to the order a dictionary happens to yield, because a matcher keyed on the first thing that fits answers about everything that fits. A tranche whose band the price has made none of the four at reaches the zone, which is the absence of the four rather than a fifth pattern: a band the price has not come back to still needs a label, and the alternatives are an empty condition or a tranche the plan does not state. The lookback of 10 sessions and the shock multiple of 3 typical daily moves are proposals under the same rule as the setups below.

**Each traded exit sells an equal fraction of what is held, and the top of the ladder trails** An exit is a fraction of a position that already exists, which is scaling out rather than sizing, so it needs no capital figure and does not touch the rule that the plan places a position and never sizes one. Equal fractions over the traded exits, because any other split is a preference dressed as arithmetic, and the skipped exit takes none. The top of the ladder is a trailing rule rather than a price, which is what figure 10.1 already says and is why the fractions divide over the traded exits rather than over five.

**A researched precondition attaches to a tranche and never creates one** A tranche can reasonably wait on something no compute component can see, a guide that does not imply a revenue decline being the case that started this. The ladder emits the tranche with its price condition, and a research pass may attach a fundamental precondition carrying its own source, which the claim checker treats like any other claim. The alternative, a fifth condition kind the ladder builder evaluates, would need the ladder to read the research store, which its matrix row does not carry and should not: a nightly component that reads research is a nightly component whose output changes when a paid pass runs. Nothing about a tranche's existence, its price, its stop or its order depends on the precondition; it is a sentence attached to a tranche that already exists.

**The event setups' triggers are proposals until resolved setups can score them** Three setups keyed to the print, each with a trigger, an entry, a stop and a target, and every figure in them is a proposal stated as one on the page, the way section 11 states the six reason thresholds. Twelve numbers invented at a planning pass and written as rules would be twelve constants nobody could later tell from measured ones, and this corpus has no basis to correct them until something has scored a setup. A breakout before the print triggers on a daily close above the immediate resistance band's high edge on volume above the fifty-day average, with the print inside the horizon and at least three sessions away; it enters at that close, stops on a daily close back below that band's low edge, and targets the next resistance band's low edge. A flush after the print triggers where the session after the print closes down by more than two typical daily moves and inside a support band; it enters on the following close once that session's low has held, stops on a daily close below the flush session's low, and targets the flush session's own open. A gap up after the print triggers where the session after the print opens above the immediate resistance band's high edge and closes above its own open; it enters at that close, stops on a daily close back inside the band, and targets the next resistance band's low edge. The book's horizon is 10 sessions from the trigger, and a setup unresolved at that cap is unresolved rather than anything else (owes: The event setups' triggers calibrated from resolved setups).

## How the picks improve

**A condition is judged against the break-even its own plan demands** Every listing carries an entry, a stop and a target, so it states the hit rate it needs to be worth taking. The score for a condition is whether its setups reached the target before the stop more often than that. A forward return over a fixed window mostly measures whether the market rose, which is why the run page shows those against the universe base rate; this score needs no such correction because the bar moves with each setup.

**A reason's record is displayed, beside the reason and never beside the name** Once a reason has enough resolved setups it shows the share that reached the target before the stop, the number resolved, and the break-even those setups demanded, always as the three together. That tells you which of tonight's reasons has a track record while you are reading. It is a property of the reason across every name it has ever fired for, so it is not placed next to a ticker, where it would be read as that stock's chance of going up.

**The record column stays empty until it has earned a number** Below the minimum the display shows how many setups have resolved against how many are needed, and no rate. That will be the state for the first year, because a list of about fifteen names a night accumulates a few hundred setups a year per reason. Lowering the minimum so the column fills sooner would put a figure on the screen that looks like evidence and is not, and a figure on a screen gets acted on.

**An unresolved setup is never a win** A setup that has reached neither its target nor its stop within the time cap is reported in its own column and excluded from the rate. This is the same rule as unexamined never counting as a pass in the harness, applied to trading outcomes.

**Candidate conditions are registered before they are scored, and scored in shadow before they are shown** The register is an append-only table naming each candidate, its rule, its test and the date it was registered, with a stated maximum family size. Rows are never updated or deleted: a retirement is a new dated row naming what it retires, which is the same convention this document uses for superseded decisions. What pre-registration needs is that you cannot quietly change what you registered after seeing the result, and append-only with an insert timestamp gives that without keeping a fact outside the store. A candidate is evaluated and stored nightly like a live condition and appears nowhere until it has cleared the minimum evidence and the corrected threshold. Nothing is adopted on the strength of the idea, and nothing is chosen after seeing which way the data went.

**The significance threshold is divided by the family size, and the divisor is shown** Running several candidates and keeping whichever looks best is the standard way a self-improving system makes itself worse while appearing to learn. Showing the divisor beside the verdict means a later reader can tell how hard the test actually was.

**Adding a candidate later restarts the clock** Registering a new candidate after the family is set inflates the family, so the correction changes and affected verdicts are recomputed. Without this the register could be widened quietly until something passed.

**Improving what surfaces a name is in scope; ranking names against each other is not** The test for any future change is whether it decides which chart is worth opening or which stock is better than another. A scoring loop makes that line easy to cross by increment, so it is stated here rather than left to judgement.

## The list

**Tonight's list is built from stated conditions, not a score** The length of the list is itself the reading, and a ranked cutoff is the same length every night so it cannot tell you whether anything happened. A condition is also a sentence you can check against the chart, where a score is a formula you would keep tuning.

**The page shows twenty and states the true count** A hundred-name night says a hundred.

**Condition thresholds are calibrated from your own nights, not from a backfill** The run page records what fired each night, so the distribution that sets the thresholds is the one you actually live with. That names no checkpoint and cannot: nights accumulate while the system runs and no checkpoint accumulates them, so the calibration is an operating obligation with a numeric trigger rather than a deferral to a phase (owes: The six reason thresholds calibrated from the nights they fired on).

**Every forward-return figure is shown against the universe base rate** Most names are higher after a month regardless, so a bare hit rate reports market drift as a finding.

**The base rate is over every name-night, and never over the listed ones** The population is every `listing` row for the window, being one per index member per night whether or not a reason fired, and not the rows where one did. `CLAUDE.md` states the same rule about this tool's own verification, and it is the same arithmetic either way: a figure computed over listed names only is a figure over the wrong population, because a listings row exists for every name. Comparing a reason's hit rate against the rate among names that fired would compare a signal against itself and report zero for a reason that works. The window is the horizon the figure is stated at, so a five-session return is shown against the five-session base rate and a twenty-one-session return against the twenty-one, and the population, the filter and the source are stated with the figure rather than beside it.

**The `setup` horizon has no universe base rate, and the column is null for it** Target before stop is a question about a plan, and a name with no plan that night has no answer to it, so there is no universe-wide figure of the same kind to pin beside it. The column is null for that horizon, as `return_pct` already is, rather than being computed over the name-nights that happened to carry a plan: that would be a base rate over a different population from the one the row is about, which is the thing this pair of decisions exists to refuse. What a setup is judged against is the break-even its own plan demanded (see: A condition is judged against the break-even its own plan demands).

**`base_rate` is stored per row on purpose, and the reason is that the row is what gets read** It is a property of the night and the horizon and it sits on a table whose grain is one row per listing per horizon, so one night's figure is repeated across the index. That is deliberate rather than a grain error. The row is what the run page reads and what a later session scores, and a figure that has to be joined for is a figure that can be shown without it; storing it beside the return is what makes "no forward-return figure without its base rate" a property of the store rather than a habit of the page. The cost is one REAL per row against a table already keeping every listing forever.

## Presentation

**One application, not a file per report** The nightly run stores data and renders nothing. Reports are rendered from stored data when read, so a layout change costs nothing and no file on disk goes stale.

**A single report can still be exported as a self-contained file** Handing one report to someone outside the tool is a stated use, and the exporter renders through the same code path.

**A screen reads and renders, and computes nothing** No screen calls a model, makes a network request, or works out a level, a stop or a rate. Every number on every screen is already in the store. A rendering layer that computes is a second implementation of the same arithmetic, and two implementations of one rule disagree eventually. It also means a screen can be rebuilt or restyled without any chance of moving a number.

**Marks are defined once and every screen draws from that list** Seven named marks, each a function from stored values to an SVG string, with no script needed to render one. Nothing on any screen is a one-off drawing. That is what lets the exported single report carry the same pictures as the application, from the same data through the same code, rather than two renderers drifting apart.

**Support and resistance own two hues and nothing else uses them** Green is a level below the price and orange is one above it, on every screen and in every mark. A day's price change in particular does not get them, because a green day beside a green support band is one colour meaning two things. Direction is carried by the sign on the number and by which side of a zero rule a bar sits on, and every band carries its role in words as well, so hue is never the only channel.

**Not yet measured is drawn as a dashed outline, never as a pale value** Anywhere a figure has not earned a number, the space carries its count against its minimum inside a dashed outline. A pale number reads as a small one, and the distinction between a small value and an absent one is the difference between a screen doing its job and a screen with no evidence.

**Every figure carries a plain-language key** A short paragraph beneath each picture explaining how to read it is the reason someone outside the domain can follow it.

**The plan figure is one vertical price column with the current price marked in it** Everything above the marker is a sale and everything below is a purchase, which is legible without reading a caption.

**Distances are stated as typical days' moves** "Two typical days away" is understood immediately where an ATR multiple is not.

**Every part of a page states where it came from and as of when** Computed tonight, fundamentals as of a filing date, research as of a date and a model.

## Where it runs

**The whole system is a checkout and one database file** Everything the system owns lives in a single database, including the text of every source document it has fetched and the candidate register. There is no directory of loose artefacts to keep in step with it, so moving an installation means copying the code and one file.

**Nothing is written against one operating system** The runtime, the database and every provider call already behave the same on Windows and on macOS. Two things would break that if left implicit, so they are decided here: no path is hardcoded, the data directory being configuration; and the nightly run is a single command that an external scheduler invokes rather than a service that schedules itself, because scheduling is the one genuinely platform-specific piece. The model endpoint is a URL in configuration for the same reason.

**The local and paid boundary is a property of the machine, not of the design** The split in section 13 is set by how much context the local model can hold, so different hardware moves it, and a machine with more memory available to the model can take more of the work locally. The comparison against the fixture is re-run after a hardware change rather than the earlier boundary being assumed to still hold.

## Process

**A frozen fixture per checkpoint, and the harness decides sign-off** Live data changes nightly and cannot be diffed; the committed fixture can. UNEXAMINED never counts as a pass.

**The fixture is diffed on each stage's serialised output, of which the facts file is one** Prose varies between runs and layout changes constantly, so diffing rendered output would fail for reasons that do not matter and pass over reasons that do. That argument is about the rendered page and holds; naming the facts file as the thing diffed narrowed it to one stage that does not exist until 5.3, leaving every expectation from 1.2 onward with nothing the record said to diff against. Each stage serialises what it produced, the membership set, the stored bars, the refusal record, the indicator rows, and the fixture diffs that. Not the store itself: diffing rows couples every expectation to schema shape, so a migration adding a column breaks expectations about values that did not change, and the fixture stops being a check on behaviour. Supersedes The fixture is diffed on the facts file, not on a rendered page.

**A research pass is recorded per section call, keyed on the canonicalised request** A pass has to replay without a network or no fixture covers research at all, and section 19.2 asked for a recording model endpoint without saying what a recording is. It is what every other outward call here already is: a captured request and response pair committed with the fixture, named in the manifest, and read by the parser the live client uses. Two things about its shape are choices a later session could reverse invisibly. It is keyed on the request rather than on the order the calls were made, because a pass that writes its sections in a different order must still replay, and a sequence-keyed recording passes on the run that produced it and fails on every other. And there is one record per section call rather than one per pass, which is what per-section dating in the research record already requires and what lets one section be run on two models over one evidence set (see: A research record is written and dated per section, not as a whole). The key is a hash of the lane, the section, the model identifier, the identifiers of the documents handed in and the prompt text, so a recording answers the request it was made for and nothing else. A replay asked for a request the recording does not hold refuses by name rather than reaching the network, which is the property the recorded feeds already have by holding no client.

**Every phase opens with something to look at** The first checkpoint of each phase renders a page. A report about row counts is not visible output.

**Facts are declared once and cited by descriptive name** Behaviour lives in this document, data shapes in section 16, and no component, decision, invariant or check carries a code number. Citations must match a name exactly, so a paraphrase fails loudly rather than resolving to the wrong thing.

**Specifications are edited clean; the changelog records what they said before** No document carries struck-through text. A superseded decision moves to section 22 with its reasoning.

**A transaction taken for speed is not asserted, and a scan that would need twelve exemptions is not written** Five stages write in a loop and open a transaction, and the question the phase 5 sign-off left open was whether a check should assert that they do. One of the five carries a correctness property and is asserted as one: `ForwardReturnFiller` interrupted partway leaves some horizons written and a base rate belonging to none of them, which is the shape the refetch's atomicity was already ruled on, so a behavioural test induces the interruption and the stage is asserted to leave nothing behind. The other four are speed at a row count the committed fixture cannot reach, and there is no reading of them a text scan can make: all sixteen writers loop, so a scan keyed on the loop reports every one of them and a scan keyed on the transaction reports none, and what distinguishes a stage that needs one is the number of rows it writes, which appears in no file's text. A scan reporting sixteen findings of which twelve are not defects is made green by exempting twelve by name, and an exemption list doing all of a check's work is the under-reporting failure `coverage-reported` exists to catch, arriving inside a check nobody needed. So the check is not written and this entry is the reason, which is the form the uncited decisions were closed on at 3.0: a citation cannot be placed at a rule that does not exist, and a check cannot be written for a property no instrument reaches.

**A written rule never blocks a real fix** If a rule in this document prevents correcting a genuine defect, the rule is the defect and is amended in the same pass, with the change stated plainly.

**A due point names a checkpoint that exists wherever its phase has been detailed** The reader that decides whether a due point is in the plan accepted the phase alone, so any point inside a phase the plan has passed whether or not its checkpoint was written. That fallback is argued for and stays where it is argued: a later phase gets its checkpoints only at the previous phase's sign-off, so requiring a checkpoint by name would forbid the check roster from naming anything past the phase in hand. The argument does not reach a phase whose checkpoints are already written. Inside a detailed phase the point exists or it does not, and a due point naming one that does not is an obligation owed at a place nobody created and a claim out of scope until a checkpoint that will never land. Found at the phase 5 sign-off, where "5.8" read as in the plan before 5.8 was written and the suite stayed green on a checkpoint nobody had created. Detail is read from the plan itself, being any checkpoint heading inside the phase, rather than from a list of detailed phases kept beside the reader, which would be a second statement of the same fact and would go stale the moment a phase is planned.

**The solution file takes the SDK's current format** The .NET 10 SDK writes `.slnx` and no longer writes the older `.sln` by default, so the solution is `EquityBrief.slnx`. Pinning the older format means every session that regenerates the file has to remember a flag to get it, and a format the tool has stopped writing drifts out of support with nothing announcing it. The corpus names the file in the layout block and in the Commands table and the suite finds the checkout by looking for it, so a format change is a rename in three places and the third one fails loudly if the other two are missed.
